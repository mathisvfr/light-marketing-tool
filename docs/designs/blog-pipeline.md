## Problem Statement

The Light marketing tool generates vacatures and marketing posts, but blog content has no pipeline. The website (lightpersoneelsdiensten.nl, Astro) has 9 static blog articles as Markdown files in `src/content/blog/`. There's no way for Sandra or Liza to create, review, or publish blog articles through the marketing tool. The `website.js` service is a stub that always returns "not configured."

The vacature pipeline works: the marketing tool writes to Supabase's `drafts` table, the website reads approved vacatures from the same database. Blogs need the same pattern.

## Demand Evidence

- **Paid maintenance arrangement** committed by Luke before the tool is live.
- **Three named users**: Luke (owner/approver), Sandra (daily content), Liza (marketing).
- **Infrastructure invested**: VPS, Docker, Buffer, Jobit feed all operational.
- **Website nearly done**: Astro site with blog pages, vacature pages, contact forms deployed.
- Growth-driven investment, not crisis-driven. Higher adoption risk but real commitment.

## Status Quo

Blog content on the website is 9 hand-written Markdown files committed to git by a developer. No non-technical user can create, edit, or publish blog content. The marketing tool has `blog` as a valid draft type in the database schema but no active flow for it.

## Target User & Narrowest Wedge

**Primary**: Sandra (content creator) enters a blog topic, AI generates the article, she reviews and submits for approval. Luke approves and it goes live on the website.

**Narrowest wedge**: Manual topic entry, AI-generated HTML blog, review, approve, live on site. AI-suggested topics deferred to a later phase.

## Constraints

- Both apps share the same Supabase instance and Docker network on the VPS.
- Blog content must follow the website's visual design (the Astro templates handle rendering).
- The marketing tool's UI is Dutch. Generated content is Dutch.
- Non-technical users -- zero-config publishing experience.
- No WordPress. No external CMS. Supabase is the data layer.

## Premises

1. Blog pipeline follows the vacature pattern: content in shared Supabase `drafts` table, website reads dynamically. Not static markdown files.
2. Existing draft lifecycle (draft -> pending_approval -> approved -> published) works for blogs. No new statuses.
3. `website.js` stub becomes a status acknowledgment. Since both apps share the DB, there's no "push" -- publishing is a status change. The website picks it up on the next request.
4. (**Revised after cross-model challenge**) Blog body stored as HTML in `blog_html` column (already exists in schema), not as a structured `{h, p}` array. More flexible for future SEO needs.
5. Existing 9 static blog articles migrated to Supabase via seed script. One source of truth.

## Cross-Model Perspective

Independent Claude subagent reviewed the premises and approach without seeing the conversation:

- **Steelman**: A closed-loop content engine where a non-technical team goes from "I have a topic idea" to "it's live on the website" in under 10 minutes, zero developer involvement. Publishing is just a status change in the shared database.
- **Key insight**: "Nobody has observed real usage yet" means every workflow assumption is speculative. Ship thin, instrument, learn.
- **Challenged premise #4**: The `{h, p}` body structure was designed for hand-written markdown, not AI-generated content. At higher velocity you need FAQ blocks, SEO schema, internal linking -- things that don't fit a flat section model. **Accepted**: revised to HTML column.
- **48-hour prototype**: Topic input -> AI generates blog JSON -> preview/edit -> approve -> status change -> website reads from Supabase. Skip criticus, images, SEO, topic suggestions.

## Approaches Considered

### Approach A: "Thin Loop" (Minimal Viable)
Blog creation page, AI generates HTML, store in existing drafts table, website reads from Supabase. No criticus, no Satori images. 1-2 days.
- **Ruled out**: User chose Full Pipeline -- wants production quality from day one since patterns already exist in the codebase.

### Approach B: "Full Pipeline" (Chosen)
Blog creation with AI generation + criticus check + Satori header image + SEO metadata. Website reads from Supabase. 3-5 days.

### Approach C: "Hybrid Source"
Keep static markdown blogs, new blogs from Supabase, website renders both sources.
- **Ruled out**: Two content sources = two code paths. Inconsistent editing experience.

## Recommended Approach

**Approach B: Full Pipeline.** The criticus check, Satori image generation, and SEO metadata patterns all exist in the codebase already. This isn't building from scratch -- it's extending proven flows to a new content type.

### Implementation Plan

#### Database Migration (prerequisite)

**0. Add blog support to drafts table**
- Migration: alter the `type` CHECK constraint to include `'blog'`: `ALTER TABLE drafts DROP CONSTRAINT drafts_type_check; ALTER TABLE drafts ADD CONSTRAINT drafts_type_check CHECK (type IN ('vacature','marketing-post','blog'));`
- Verify columns `blog_titel`, `blog_html`, `image_path`, `criticus_passed`, `criticus_notes` exist on the `drafts` table. If any are missing (CLAUDE.md schema may not match actual migrations), add them in the same migration.

#### Backend Changes

**1. Blog draft support** (`routes/drafts.js`)
- Accept `type='blog'` in draft creation.
- `form_data` contains: `onderwerp` (topic), `categorie` (one of: Uitzendwerk, Bedrijfsnieuws, Voor werkzoekenden, Voor opdrachtgevers, Wet- en regelgeving), `toon` (tone guidance, optional).
- After creation, POST `/api/drafts/:id/generate` triggers AI generation.

**2. Blog generation prompt** (`prompts/blog.md`)
- System prompt: brand context + blog writing guidelines.
- Input: topic + category + tone + brand settings.
- Output: JSON with `blog_titel`, `blog_html` (full HTML article body), `teaser` (max 220 chars), `lead` (opening paragraph, 1-2 sentences, rendered prominently on the detail page), `meta_description` (max 160 chars), `leestijd` (estimated read time).
- No `{h, p}` array. One HTML string with semantic headings (`h2`, `h3`), paragraphs, lists, and optional FAQ sections.
- `author` and `authorRole` are derived from the `created_by` user record (users table: `name` and `role`).

**3. Claude service extension** (`services/claude.js`)
- `generate('blog', formData)`: loads `prompts/blog.md`, calls Anthropic API, parses JSON response.
- Store result in `blog_titel`, `blog_html`, and `form_data` (teaser, lead, meta_description, leestijd).
- Generate a stable `slug` on first save: `${slugify(blog_titel)}-${id.substring(0,8)}`. Store in `form_data.slug`. Once set, never changes -- protects published URLs from title edits.

**4. Criticus check for blogs** (`prompts/criticus.md`)
- Extend criticus prompt to handle blog content: check brand tone, no fabricated claims, proper Dutch, CTA present, no placeholder text.
- `criticus_passed` and `criticus_notes` already exist on drafts table.

**5. Satori blog header image** (`services/render.js`)
- New template: `blog-header` -- Light branding, blog title overlaid, category badge.
- `renderSocialImage('blog-header', { titel, categorie })` -> PNG.
- Store path in `image_path` column.
- **Satori CSS limitation risk**: if the header template needs complex layout (gradients, background-image), Satori may not support it. Fallback: static placeholder image per category, same as vacatures use per sector.

**6. Website adapter** (`services/channels/website.js`)
- Replace stub with real adapter.
- `publish(draft)`: verify draft has `type='blog'` and `status='published'`. Since the website reads from the same Supabase instance, publishing is implicit -- just return `{ status: 'success', externalId: draft.id }`.
- `expire(draftId)`: update draft status, website stops showing it on next request.
- Record publication row: `channel='website'`, `via='website'`, `status='success'`.

**7. Migration: seed existing blogs**
- One-time migration script that reads the 9 static Markdown files from `light-website/far-flare/src/content/blog/`. Verify files still exist before writing the script (check git if removed).
- Parse frontmatter (title, category, teaser, date, readTime, author, lead, body), convert `{h, p}` body array to HTML, insert into `drafts` table with `type='blog'`, `status='published'`, `created_at` set from the original date.
- Generate stable slug from original filename. Store in `form_data.slug`.

#### Frontend Changes

**8. Blog creation page** (`pages/BlogAanmaken.jsx`)
- Form: Onderwerp (topic textarea), Categorie (dropdown, 5 options), Toon (optional text input).
- "Genereer" button -> skeleton loading -> preview.
- Preview: rendered blog title + HTML body + teaser + header image.
- Editable fields: title (text input), body (textarea showing raw HTML for v1 -- rich text editor like TipTap deferred), teaser, lead, image (upload override).
- Criticus result displayed (pass/fail + notes).
- Action buttons: "Opslaan als concept" / "Indienen ter goedkeuring" / "Goedkeuren" (owner).

**9. ContentWachtrij extension**
- Show blog drafts alongside vacatures and marketing posts.
- Blog type badge (distinct color).
- Same approval/rejection flow.

**10. Gepubliceerd extension**
- Blog section: list published blog articles with title, date, category, website status badge.
- Link to live article on website (construct URL from slug).

#### Website Changes (light-website/far-flare)

**11. Blog data source switch** (`src/lib/blog.ts`)
- Replace Astro content collection reader with Supabase query:
  `SELECT * FROM drafts WHERE type='blog' AND status='published' ORDER BY created_at DESC`
- Map columns: `blog_titel` -> title, `blog_html` -> body, `form_data->>'categorie'` -> category, `form_data->>'teaser'` -> teaser, `form_data->>'lead'` -> lead, `image_path` -> image, `form_data->>'slug'` -> slug.
- Derive `author` and `authorRole` from the `created_by` join to `users` table (name, role). For migrated static articles, store original author in `form_data`.
- Format `created_at` as Dutch locale date string: `d MMMM yyyy` (e.g. "3 september 2026") via `parseDutchDate()` compatibility.

**12. Blog detail page update** (`src/pages/blog/[slug].astro`)
- **Critical: convert from SSG to SSR.** The current page uses `getStaticPaths()` which prebuilds pages at deploy time. With Supabase as the data source, new blogs won't appear until the next deploy. Remove `getStaticPaths()`, add `export const prerender = false` to make it server-rendered on each request.
- **Rewrite body rendering.** The current template iterates over `article.body` as an array of `{h, p}` objects. Replace this loop with a single `<Fragment set:html={article.body} />` to render the HTML string from `blog_html`. This is trusted content (comes from the marketing tool, not user input).
- **Related articles.** The current page receives `all` articles via `Astro.props` from `getStaticPaths`. After removing `getStaticPaths`, query Supabase directly for related articles (same category, exclude current, limit 3).
- Render `lead` as the prominent opening paragraph (existing `<p class="light-lead">` element).
- Display header image from `image_path`.
- Keep existing layout, typography, and styling.

**13. Blog listing page update** (`src/pages/blog/index.astro`)
- **Convert from SSG to SSR**: add `export const prerender = false`. (This page does not use `getStaticPaths` -- it calls `listArticles()` directly.)
- Read from Supabase instead of content collection.
- Keep existing card layout, category filtering, search.

**14. Remove static blog content**
- After migration and verification, remove `src/content/blog/` directory.
- Remove content collection schema for blogs from `src/content.config.ts`.

### Data Flow

```
Sandra types topic + category in marketing tool
  -> AI generates: blog_titel, blog_html, teaser, lead, meta_description, leestijd
  -> Criticus checks quality
  -> Satori generates header image
  -> Sandra reviews, edits, submits for approval
  -> Luke approves (status -> 'published')
  -> website.js records publication row (status: 'success')
  -> Website's next request reads the new blog from Supabase
  -> Blog appears on lightpersoneelsdiensten.nl/blog/[slug]
```

## Open Questions

1. **Read time calculation**: Should AI estimate it, or calculate from word count (Dutch avg ~200 words/min)?
2. **Blog image dimensions**: What aspect ratio does the website's blog layout expect for header images? Need to match Satori template to website CSS.
3. **Internal linking**: Should AI-generated blogs link to related vacatures or other blog posts? Deferred for now but the HTML format supports it.
4. **SEO structured data**: Should the website add JSON-LD Article schema? Easy to add but not in v1 scope.
5. **Cache invalidation**: After converting blog pages from SSG to SSR, each request queries Supabase fresh. If performance becomes an issue, add Astro response caching with a short TTL (e.g., 5 minutes).

## Success Criteria

1. Sandra can create a blog post in the marketing tool, from topic to published, in under 15 minutes.
2. Published blogs appear on the website within one page load (no rebuild needed).
3. The 9 existing static blogs appear identically after migration.
4. Criticus catches off-brand content before it reaches the approval queue.
5. Header images are branded and consistent with the Light design system.

## Dependencies

- Website repo (`light-website/far-flare`) changes must be deployed alongside marketing tool changes.
- Satori blog-header template needs design tokens from the brand design system.
- `prompts/blog.md` needs writing and testing against real topics.

## Eng Review Amendments (2026-09-03)

Findings from /plan-eng-review, folded into the plan:

1. **normalizeDraftType()**: whitelist all three types explicitly ('vacature', 'marketing-post', 'blog'). Reject unknown types with an error. (Step 1)
2. **Image URL resolution**: website constructs full image URL as MARKETING_TOOL_URL + image_path. Add MARKETING_TOOL_URL env var to far-flare. (Step 11)
3. **RLS policy**: add policy for anon reads where type='blog' AND status='published'. Also fix existing vacature policy to use status='actief' (currently checks 'approved' which never matches). (Step 0)
4. **Vacature status bug**: website queries status='approved' but marketing tool sets status='actief'. Fix vacatures.ts to query 'actief'. (Bundled with step 0/11)
5. **drafts.js save-logic**: add explicit type='blog' branch in the generate-response handler (drafts.js:482-509) that saves blog_titel, blog_html to columns and teaser/lead/meta_description/leestijd to form_data. (Step 1)
6. **Author in form_data**: store author name and role in form_data on blog creation (from created_by user record). No users table join from website -- avoids exposing password_hash via anon key. (Steps 3, 11)
7. **Seed migration**: inline 9 INSERT statements with pre-parsed content, not a script that reads cross-repo files at runtime. (Step 7)
8. **Sitemap**: add dynamic sitemap entries for SSR blog pages (customPages or custom integration). (New step 13.5)

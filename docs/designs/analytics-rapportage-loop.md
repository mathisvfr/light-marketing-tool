Handoff timing surfaces the question: what analytics do we actually need to ship, for whom, in what shape?

## Status Quo

- **Sandra:** produces reports manually today, most likely by pulling from Buffer's UI, Indeed/Jobbird UIs, and Slack/email anecdote. The exact tab list is unconfirmed and part of the assignment below.

- **Jobit stats method:** unconfirmed (API? CSV export? scheduled feed pull?). Per CLAUDE.md "nog te bevestigen."

## Target User & Narrowest Wedge

- **Primary user of the tool:** Sandra, opening it weekly (or on Light's reporting rhythm).
- **Real audience of the data:** Sandra's reader — one degree upstream, the actual decision-maker.
- **Wedge:** a single `/rapportage` page with 3–6 tiles showing the metrics Sandra's reader reacts to. The specific metrics are an outstanding interview question, not a design decision.

## Constraints

- Dutch UI throughout (Nederlands).
- Dashboard shape (Light preference). No PDF-first workflow.
- Handoff timing means we ship in weeks, not months.
- Data sources have different maturity: Buffer (API live, latency-prone), publications table (own data, live), Jobit (unknown), website (stub until own site is live).
- Buffer analytics API: rate limits and 24–48h latency mean live-fetch on page load will feel broken on the Monday mornings Sandra actually opens the page.

## Premises

1. Sandra is the primary analytics user, not Luke.
2. Dashboard must answer Sandra's reader's questions — not "show all the data."
3. Dashboard UX must feel professional and shareable — the surface Sandra hands upward. Clean, not chrome-heavy. (Revised in Phase 3.5 based on cold read.)

5. We don't yet know which 3–5 metrics Sandra's reader specifically reacts to. Blocking assumption; addressed in "The Assignment."

## Approaches Considered

### Approach A — Rapportage v0 (subagent's exact prototype) — NOT SELECTED

Single `/rapportage` page, 6 hard-coded tiles, one query per tile, nightly Buffer snapshot, manual paste-in for Jobit. Ships in 3–4 days of human time / ~30 min CC. Rejected in favor of B because the tool has three data sources at different maturity levels (Buffer live, publications live, Jobit unknown, own website coming) and B's abstraction pays for itself when sources stabilize.

### Approach B — Extensible Metrics Layer — SELECTED

Same visible UX as A on day one, but backed by a `metric_snapshot` table and per-source snapshotter services. Details in "Recommended Approach."

### Approach C — Weekly Report Generator (lateral) — NOT SELECTED

Reframe: primary UX is "Nieuw rapport" → shareable HTML page, dashboard becomes archive. Rejected because Light explicitly said "no PDFs," and rich-HTML-shareable is PDF-adjacent enough to risk a "not what we wanted" review at handoff.

## Recommended Approach: Extensible Metrics Layer

### Sequencing (the honest tension with The Assignment)

The Assignment says interview Luke and Sandra before writing the first snapshotter. Approach B pre-commits to an abstraction *before* the interview confirms which metrics matter. This tension is real. Resolution:

- **Week 0 (this week):** run the interview. If Sandra's reader has a narrow, stable metric set that lives entirely inside our own DB, drop back to Approach A and reconsider the snapshot table entirely.
- **Week 1 (if the interview confirms multi-source metrics):** ship the `metric_snapshot` table, `db_snapshotter`, `manual_snapshotter`, and the UI shell.
- **Week 2:** ship `buffer_snapshotter` with the rate-limit cap, run backfill.
- **Later:** activate `jobit_snapshotter` and `website_snapshotter` when their source methods are confirmed.

If the interview fails to happen in Week 0, do **not** start building B — ship a shell page with just the four DB-derived tiles (A-shape) and revisit.

### UI (day one)

- One page: `/rapportage`, single scrollable view, Dutch UI.
- Date range picker only: **Deze week / Deze maand / Aangepast**. No drilldown. No per-vacature filters.
- Six tiles in this order:
  1. **Actieve vacatures** — count from `drafts` where `status='actief'`.
  2. **Nieuwe vacatures deze week** — count from `drafts.created_at` in range.
  3. **Marketingposts gepubliceerd** — from `publications` where `via='buffer'` and `status='success'`.
  4. **Per-kanaal breakdown** — bar chart of publications counts per channel (LinkedIn / Facebook / Instagram).
  5. **Buffer engagement** — aggregated likes / comments / reach across period. Reads from snapshot, never live.
  6. **Vacature-bereik (Jobit)** — clearly labeled work-in-progress. Owner sees a paste-in form with three fields: `weeknummer` (int), `totaal_bekeken` (int), `totaal_sollicitaties` (int), plus an optional `bron` free-text note. Non-owners see the resulting numbers read-only. A "Wordt binnenkort volledig gekoppeld" indicator sits above the form. Note on premises #4 + #5: shipping this manual-paste interim depends on Sandra actually pasting weekly. Measurable failure mode: zero paste-in rows after 30 days ⇒ Jobit stats are lower-priority than assumed and the real integration can slide.

### Data plumbing (the B part of B)

- **New table:** `metric_snapshot`
  ```sql
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  metric_key    TEXT NOT NULL,        -- 'buffer.engagement.likes', 'drafts.actief.count', etc.
  dimensions    JSONB NOT NULL DEFAULT '{}',
  value         NUMERIC,
  value_json    JSONB,
  captured_at   TIMESTAMPTZ NOT NULL,
  bucket_date   DATE GENERATED ALWAYS AS ((captured_at AT TIME ZONE 'Europe/Amsterdam')::date) STORED,
  source        TEXT NOT NULL         -- 'buffer','db','manual','jobit','website'
  ```
  Unique upsert key: `UNIQUE (metric_key, bucket_date, md5(dimensions::text))` — one row per metric per day per dimension-set. Snapshotters upsert via `ON CONFLICT (metric_key, bucket_date, md5(dimensions::text)) DO UPDATE`. Read index: `(metric_key, captured_at DESC)`.

- **Snapshotter base contract** — every snapshotter exports one function:
  ```
  async run({ from: Date, to: Date, db, log }) → { written: number, skipped: number, errors: [] }
  ```
  Snapshotters are idempotent per `(metric_key, dimensions, captured_at date)`: re-runs upsert, never duplicate.

- **Day-one snapshotters** (in `backend/src/services/metrics/`):
  - `buffer_snapshotter.js` — nightly cron. Iterates published posts in the last 30 days via `publications` where `via='buffer'`, oldest-refresh-first (cursor: `last_snapshotted_at` on each publication row). Rate-limit strategy: sleep-and-retry on 429 with exponential backoff. Per-run hard cap 100 API calls (revised at build time once Buffer Free-tier ceiling is confirmed). Unfinished posts resume on the next night from the cursor — full 30-day coverage refreshed within a few nights even under a tight cap.
  - `db_snapshotter.js` — reads `drafts` and `publications` directly, writes count / breakdown snapshots. Runs nightly and on-demand from `/rapportage` when the newest snapshot for a key is >6h old.
  - `manual_snapshotter.js` — writes Sandra's paste-in through `POST /api/rapportage/manual`. See paste-in schema in tile 6 below.

- **Stubs (day-one contracts, no runtime yet)** — these ship as the base-contract signature only, no scheduled runs:
  - `website_snapshotter.js` — activated when the own-site adapter is chosen (interne REST vs shared Postgres, still TBD).
  - `jobit_snapshotter.js` — activated when Jobit's stats-back method is confirmed.

- **Scheduling:** `node-cron` in-process inside the existing single backend container. Job registration in `backend/src/index.js` at startup, so container restart re-arms the cron on next boot (no external scheduler). Nightly run at `0 3 * * *` in `Europe/Amsterdam` (matches Light's business timezone; "Deze week" boundaries computed in the same TZ). **Single-runner guarantee:** the deployment is one backend container (per CLAUDE.md docker-compose). If we ever scale to N replicas, add a Postgres advisory lock (`pg_try_advisory_lock('metric_snapshotters')`) inside each job entry point — noted here so the migration to multi-replica doesn't double-fire the cron.

- **Backfill:** on first cron run, walk backward 90 days for `buffer_snapshotter` and `db_snapshotter`. Manual and stub snapshotters have no backfill (nothing to fetch).

- **Retention:** keep 400 days of snapshots (covers year-over-year comparison). Daily prune job removes rows where `captured_at < now() - interval '400 days'`.

- **Dashboard reads exclusively from `metric_snapshot`.** No live third-party fetches on page load. Page renders <500ms target — measured with the existing `/api/*` timing middleware; log a warning above 500ms so we notice regressions.

- **Empty / stale state:** if the newest snapshot for a tile's metric is missing or older than 36h, the tile renders a Nederlandse "Data verouderd — laatste update {relatieve tijd}" chip in the tile header rather than a broken chart. `/rapportage` never shows a blank page — always at least the count tiles from `db_snapshotter` (which is on-demand-refreshable).

### Access control

- `GET /api/rapportage` (data endpoint) — requires any authenticated user (owner, recruiter, or viewer). Read-only.
- `POST /api/rapportage/manual` (paste-in endpoint) — `requireRole('owner')`. Recruiter/viewer cannot inject stats.
- The `/rapportage` UI is visible in the sidebar to owner + recruiter + viewer; the paste-in field on tile 6 is only rendered for owners.

### Migrations

- `018_metric_snapshot.sql` — the new table + indexes. (Manual paste-in lives in `metric_snapshot` with `source='manual'`; no separate table.)
- Aware of `013_drafts_history_and_publications_metrics.sql`: the existing per-publication metrics stay where they are; the snapshot table is a rollup / cross-source layer, not a replacement.

### Testing

- Per-snapshotter backend test with the outbound API mocked, verifying a snapshot row is written with the expected shape.
- Integration test: `/rapportage` returns the latest snapshot per metric within the requested date range, purely from the DB.

## Success Criteria

- Sandra opens `/rapportage` on her reporting rhythm and sends her reader the numbers (screenshot, copied text, or link) without opening any other tool.
- Sandra's reader takes at least one visible action (question, meeting, decision) based on numbers from the tool within 30 days of handoff.
- Page renders in under 500ms from `metric_snapshot`; no live third-party fetch on page load.
- Adding a new metric source in month 2 or 3 = implement the base-contract `run(...)` function and register the cron entry, no dashboard rewrite.
- Manual paste-in for Jobit gets used at least once by Sandra before the real integration is wired. If it never gets used, that's a signal Jobit stats are lower priority than assumed.

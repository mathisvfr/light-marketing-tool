## Problem Statement

Light Personeelsdiensten's marketing tool is functionally complete and has active weekly users (Luke, Sandra, others). But every failure routes through the developer personally via WhatsApp/email. Users retry multiple times, then message Martijn, who context-switches to diagnose and fix. The tool needs to handle its own errors so users are self-sufficient.

The two flows that matter: **generation** (idea to content) and **publication** (content to live channels via Buffer/Multiposter). Everything else is secondary.

## Demand Evidence

- 3-4 non-technical users use the tool weekly for real work (vacatures, marketing posts, blogs)
- When it breaks: "They send me an email or whatsapp message, they wait for me to fix it after retrying multiple times" -- the developer is the error handler
- Today's session started with a real user report: Luke tried to add Instagram to an existing LinkedIn post and everything regenerated from scratch. Sandra hit Buffer rate limits with English error messages.
- Both issues were fixed in the same session before this design doc was written.

## Status Quo

- Users have no workaround beyond messaging Martijn. No fallback to manual posting, no self-service recovery.
- The developer diagnoses from WhatsApp descriptions, not from logs or structured error data.
- Generation failures show generic or English error messages. Users don't know what went wrong or what to do about it.
- Autosave silently fails -- users don't know their edits were lost until they reload.
- No backend input validation -- malformed requests hit Claude and produce garbage.

## Target User & Narrowest Wedge

- **Primary users:** Luke (recruiter, creates vacatures and marketing posts) and Sandra (reporter, creates content and tracks what was published)
- **Wedge:** Make the generation and publication flows self-recovering. When something fails, the tool tells the user what happened in Dutch, offers a retry button, and only escalates to Martijn when something is genuinely unrecoverable.

## Constraints

- Dutch UI throughout
- Same stack (React 19 + Express + Supabase) -- no rewrites
- Docker Compose + Caddy deployment on VPS
- 3-4 people work on the codebase weekly -- test coverage needed so changes don't break things
- Developer has not observed users using the tool directly (only bug reports via text)

## Premises

1. Generation flow and publication flow are the two things that matter. Everything else is secondary.
2. The tool needs to handle errors gracefully on its own so users stop messaging the developer.
3. Backend needs more test coverage on critical paths before adding new features.
4. Frontend resilience matters as much as backend correctness.
5. Developer should watch someone use the tool to discover issues bug reports don't surface -- but don't wait to fix known issues.

## Cross-Model Perspective

Independent Claude subagent cold read:

- **Steelman:** "A single pane of glass where a recruiter types a job brief and within 60 seconds has publish-ready, brand-compliant content across 30+ job boards, three social platforms, and their own website. If it works reliably, it replaces an agency's worth of copywriting and social media management for a team of three."
- **Key insight:** "Every minute spent on new features before fixing error handling is negative-value work. The tool does not need to be smarter. It needs to be boring."
- **Challenged premise #5:** "The failure modes are already known. The WhatsApp thread is full of bug reports. The codebase audit found concrete issues. You don't need a usability session to know that 'generation fails and the user sees nothing useful' is the #1 problem." Test: if WhatsApp goes quiet after fixing the top 5 issues without ever doing observation, premise #5 was unnecessary.
- **48-hour plan:** Same stack, no rewrites, pure resilience engineering. Structured logging, input validation, retry, optimistic locking, error boundaries, autosave surfacing, channel health bar.

Synthesis: both models agree on the fix list and the "be boring" principle. Disagreement on observation -- resolved by doing both (fix now, observe after).

## Approaches Considered

### Approach A: "The Boring Sprint"
Fix the 6 highest-impact resilience issues. No tests, no monitoring, no architecture. 2-3 sessions. Fixes today's bugs but doesn't prevent tomorrow's. Rejected: too narrow for a codebase with 3-4 weekly contributors.

### Approach B: "Production Grade" (chosen, then cherry-pick from C)
Everything in A, plus test coverage on critical paths, structured logging, channel health monitoring, and a user error reference. 4-6 sessions. Stops WhatsApp messages AND prevents new ones.

### Approach C: "Full Professionalization"
Everything in B plus frontend testing infrastructure, E2E tests, CI pipeline. 8-12 sessions. Risk of losing momentum. Cherry-picked: CI pipeline + frontend test setup come after B lands.

## Recommended Approach

**B, then cherry-pick CI + frontend tests from C.** Ship resilience, then lock it down with infrastructure.

### Phase B: Production Grade (4-6 sessions)

**Session 1: Frontend resilience**
1. API client (`frontend/src/lib/api.js`): Add 30-second AbortController timeout, 1 automatic retry on 5xx/network error for GET requests only (POST/PATCH/DELETE are not retried to avoid duplicates), error toast notification. Note: server-side Buffer retry (exponential backoff on 429) was already shipped today -- this is a complementary frontend-level resilience layer.
2. Error boundaries: a global ErrorBoundary already wraps the app in App.jsx with Dutch messaging. Add three additional subtree-level boundaries nested inside it for granular isolation: generation preview, content queue/approval, publish flow. Each shows a Dutch error with a per-section retry button so a crash in generation doesn't take down the queue.
3. Autosave error surfacing: `useAutosaveDraft` already returns `{ error }` and pages render `.autosave-indicator.error`, but the indicator is small and easy to miss. Enhance it: add a prominent red banner "Wijzigingen niet opgeslagen" that persists until the next successful save, plus a manual "Opslaan" fallback button for when autosave is stuck.

**Session 2: Backend validation + locking**
4. Input validation on `POST /api/drafts` and `POST /api/drafts/:id/generate`: required fields, length limits, type checks. Dutch error messages ("Titel is verplicht").
5. Optimistic locking on draft approval: add `version` integer column, conditional UPDATE WHERE version = expected. Only status-changing operations (approve, reject, submit, publish) increment the version. Autosave PATCHes to form_data do NOT increment the version -- they're content edits, not lifecycle transitions. This means an approval can race with an autosave without conflict, but two concurrent approvals will correctly block each other.
6. Dutch error audit: find and translate any remaining English error messages across all routes.

**Session 3: Backend test coverage - generation flow**
7. Tests for `POST /api/drafts` (validation, creation, rejection of bad types) -- ~5 tests
8. Tests for `POST /api/drafts/:id/generate` (mock Claude, test partial generation, test error paths, test channel-only generation) -- ~10 tests
9. Tests for approval flow including race condition (concurrent approve) -- ~5 tests

**Session 4: Backend test coverage - publication flow**
10. Tests for `POST /api/publish/:id` (mock Buffer, test retry, test partial channel failures, test scheduling) -- ~10 tests
11. Tests for `/publish/:id/retry-failed` (retry only failed channels, verify new publication rows) -- ~5 tests
12. XML feed edge cases: feed with special characters, zero vacatures, plaats validation -- ~3 tests

**Session 5: Monitoring + user reference**
13. Channel health endpoint: check Supabase connection, Claude API reachability, Buffer API reachability. Frontend status bar (green/yellow/red).
14. Structured error logging with request IDs (consider pino or stick with console.log + JSON format)
15. "Wat te doen bij problemen" reference card: 3 scenarios (generation fails, publish fails, error screen), each with what you see / what to try / when to message Martijn.

**Session 6: Integration + verification**
16. End-to-end manual walkthrough of both flows with all fixes in place
17. Deploy to VPS
18. Monitor WhatsApp volume over next week

### Phase C cherry-picks (after B lands):
- GitHub Actions CI (backend tests + lint + build on PR)
- Vitest + React Testing Library setup
- Frontend tests for MarketingPost and VacaturePlaatsen generation flows

## Open Questions

- Should structured logging be pino (new dep) or formatted console.log with JSON? Pino is better but adds a dependency.
- Channel health checks: how often? Every 60s via backend cron, or on-demand when user opens the dashboard?
- After the observation session: what additional issues surface that change the priority order?

## Success Criteria

1. **WhatsApp volume drops 70%+** within 2 weeks of deploying all fixes
2. **Zero full-app crashes** from component errors (error boundaries catch them)
3. **Critical-path test gaps are closed** -- existing tests cover drafts (13 blocks in drafts.test.js), publishing (4 in publish.test.js), feed (4 in feed.test.js), and E2E flow (flow.test.js). Gaps: input validation on /drafts, partial channel generation, concurrent approval race, publish retry-failed, scheduling per channel. Target: ~20 new tests covering these specific gaps.
4. **Every user-facing error message is in Dutch** with an actionable suggestion
5. **Autosave failures are visible** to the user within 2 seconds

## Dependencies

- **Server-side Buffer retry** (exponential backoff on 429, Dutch error translation) already shipped today (2026-10-16). Session 1's API client retry is a separate frontend-level resilience layer for all API calls.
- **Channel-addition partial generation** (only generate missing channels, preserve existing content) already shipped today.
- **Auth bypass on GET /drafts/:id** already fixed today (added canEditDraft ownership check).
- Jobit/Multiposter integration fixed yesterday (2026-10-15).
- No external dependencies beyond what's already in the stack.

- When I asked about watching users, you said "Nope, just the emails and texts" without defensiveness. That honesty is more useful than a founder who invents observation stories. Most people would say "yeah, kind of" and move on.
